# 第 7 章　岗位让位于闭环

有一家公司，二十年来只干一件事，把它干成了一门独门本事，它叫帕兰提尔（Palantir）。

它最值钱的资产，是一群被派到客户现场的工程师。它不像别的软件公司那样，把工程师留在总部写代码、再让销售拿去卖，而是把人直接派到客户那里，蹲在客户的分析师、操作员旁边，看他们真实怎么干活，然后就地把软件写出来、接上数据、推上生产。

帕兰提尔真正的精妙，不在派人下去，在它那套角色分工。它把现场的活分给两种人。一种盯着该解决哪个问题、用户到底怎么干活、怎么让人真用起来；另一种盯着快速把能跑的软件建出来。这两种人并肩作战，一个管问题选对没有，一个管东西建出来没有。他们身后还有一群产品工程师，专门把现场反复出现的模式，沉淀成平台的通用能力。

看清楚这个结构。帕兰提尔的交付单元，不是一个岗位，是一支围绕把客户某个问题真正解决掉这个结果、临时编成的小队。问题解决了，现场的经验被产品工程师收走、变成平台能力，下一次就从更高的起点重新开始。

这套二十年前就跑通的东西，预演了 agent 时代最深的一个组织变化。工作的基本单元，正在从岗位，变成闭环。

---

上一章借巴纳德讲清了组织为什么形成，它是一套靠共同目的、沟通、贡献意愿维系的协作系统。这一章问下一个问题，这套协作系统，为什么要长成岗位、部门、汇报线的样子。

答案还是巴纳德那套，只往前推了一步。一个协作系统要稳定运转，就得回答谁负责什么、信息怎么流、决策在哪做。于是岗位出现了，它是一个稳定的责任包，这个位置负责这些事、向谁汇报、和谁协作。部门、层级、流程，都是围绕岗位这个原子搭起来的。

这套岗位化的逻辑，一百年来解决了一个真实的问题。当协作的规模大到没人能事事亲为，你需要把谁干什么固定下来，否则每件事都要重新协调一遍，组织会瘫在无尽的沟通里。岗位是用稳定换效率，你牺牲一点灵活，换来不必每次都重新分工。巴纳德看得很透，组织的存续靠协作关系的稳定，而岗位正是让协作关系稳定下来的那个装置。

但岗位有个代价，一百年来大家忍着。它是围着人和职能切的，不是围着结果切的。一个客户的问题，往往要跨好几个岗位、好几个部门才能解决，销售接单、产品设计、工程实现、客服跟进，中间全是部门墙、交接、扯皮。结果被岗位切成了碎片。

在人的时代，这个代价只能忍。因为围绕每一个结果临时组一个跨职能小队，协调成本太高，找人、对齐、沟通，比部门墙的损耗还大。现在，这个成本正在塌下去。

---

巴纳德的核心，组织是围绕共同目的的协作系统，在 agent 时代不但成立，而且终于能被兑现了。

巴纳德一直说组织的灵魂是共同目的。可在岗位化的组织里，共同目的常被岗位切碎，每个岗位盯着自己那一亩三分地的 KPI，谁也不为最终那个结果整体负责。agent 时代能做的，恰恰是让协作重新围着目的转，而不是围着岗位转。这是对巴纳德的兑现，不是背离。

但兑现的方式，是巴纳德没见过的。Agent Harness 让 agent 能持续干活、能被编排，更要紧的是，它把围绕一个结果临时组队的协调成本压到了极低。你不用开会、发邮件、走流程去协调一支跨职能小队，可以直接把人和 agent 编成一个盯着同一个结果的单元。

于是有了帕兰提尔那种人加 agent 的部署小队，也有了一些前沿公司把交付单元做成一个 pod 而非一个工程师的结构，里面有领域操作者、客户工程师、现场工程师、交付负责人、高管发起人，还有一条回流到模型团队的反馈通道。这个单元不对应任何一个传统岗位，它对应一个结果。

还有一个耐人寻味的现象。不少用了 AI 的公司，工作流变了、职责变了，可正式的汇报线基本没动。道理不难想，改工作流很快，本地就能改；改汇报线很慢，牵扯预算、编制、职业路径、权责。这说明岗位正在被架空，真实的工作已经围着结果重组了，只是那张挂在墙上的岗位图还没跟上。

巴纳德的协作系统要落地，过去只能落成岗位，现在，它能落成闭环了。

---

把这条线捋到底，组织的基本原子就该换了。它从岗位，一个稳定的责任包，变成结果单元，一个围绕端到端结果编成的人机闭环。

过去是先有岗位，再把结果切成碎片分给各岗位。现在是先有结果，再围绕它临时编一个人加 agent 的组织阵型，端到端地把它闭环。

这个单元有几个和岗位很不一样的地方。它围着结果转，对什么结果负责就编什么阵型。它跨越传统边界，人和 agent、不同职能，为同一个结果编在一起。它用完能重组，结果达成，经验沉淀进平台，阵型可以解散重编。帕兰提尔那套现场解第一例、沉淀进平台、下次从更高起点开始的循环，就是这种结果单元的成熟形态。

这里要小心一个误读，这不是说岗位立刻消失了。汇报线、职级、部门还会存在很久，它们牵扯的东西太重。真正在变的是工作实际怎么组织，越来越多的活，是围绕一个结果、由一个临时的人机阵型闭环掉的，而不是在岗位之间一棒棒传递的。岗位图还挂在墙上，但活已经不那么干了。管理者要做的，是别再盯着那张越来越失真的岗位图，转而去设计结果单元，想清楚这个结果要什么阵型、谁供判断、谁供执行、怎么闭环。做法是围绕结果重新编阵，而不是给现有岗位外挂几个 agent 了事。

---

要围绕一个结果编一个单元，而不是往旧岗位上贴 agent，先答这几问。

| 问题 | 要钉死的 |
|------|---------|
| 这个单元对什么结果负责？ | 一个端到端的、可验证的结果，比如把首解率提到八成，而不是笼统的"负责客服" |
| 这个结果要什么阵型？ | 需要哪些人、哪些 agent、哪些技能，按结果配，不按现有编制配 |
| 谁供判断，谁供执行？ | 人守住问题选择、风险判断、组织权威，agent 供执行力 |
| 怎么闭环？ | 结果达成后，经验怎么沉淀（进平台、知识库、技能），阵型怎么重组 |
| 和旧岗位图什么关系？ | 明确这个单元横跨了哪些传统岗位、部门，这些墙就是它要打穿的 |

这张卡的用法是倒过来的。先问我要这个结果、该编一个什么样的人机阵型，而不是先盯着手里这些岗位、琢磨怎么塞 AI。从结果出发，这就是从岗位到闭环的全部。

---

围绕结果编成的单元，跑起来靠什么。靠每个成员，不管是人还是 agent，都能理解并执行一套标准的做事方法。帕兰提尔的小队能高效，正因为它把大量做事的方法沉淀成了平台上可复用的东西。

这里有个新问题。在岗位时代，方法是写给人看的文档，SOP、操作手册、培训材料，人读了、懂了、照着做。可 agent 不读文档，它需要的是能被它直接调用、直接执行的东西。当团队里一半是人、一半是 agent，标准化这件泰勒开创的老事，会变成什么样，一份 SOP 怎么才能同时被人读懂、被 agent 执行。这是下一章的事。
